Verify or refresh the Espalier-Harness integrity manifest.

The integrity manifest (`.espalier/integrity.json`) tracks hashes of the harness
files it manages (built and updated by `espalier integrity refresh .`). The hash
is taken over each file's canonical text form -- a leading UTF-8 BOM stripped,
line endings folded to LF -- under the algorithm name `sha256-lf`, so a checkout
git re-ended to CRLF is not drift; a manifest written under the older raw-bytes
name `sha256` still verifies until its next refresh, and `integrity verify`
reports the manifest's algorithm and says so once. The writer follows the
DEPLOYED hooks' name: an engine upgraded ahead of its hooks keeps writing the
raw-bytes manifest and tells you to run `espalier upgrade --execute`; a manifest
the deployed hooks cannot read is reported as "newer than the hooks" with the
same remedy, never as drift. When it drifts,
`session_start.py` reports drift at session start (visibility-only audit + stderr
warning — SessionStart cannot block per the hook protocol). The blocking
surfaces are PreToolUse (`write_guard.py` denies tool calls while a kill-switch is
set), ConfigChange (`config_guard.py` denies unsafe settings changes), and CI
(`ci_guard.py` backstops a force-added kill-switch; `.claude/settings.json` is
gitignored, so the normal commit path cannot carry one).

## Verify current state

```bash
python -m espalier integrity verify .
```

Reports any files whose hash has changed since the last refresh.

## Refresh after intentional changes

Run this after any intentional modification to harness files:

```bash
python -m espalier integrity refresh .
```

Updates the manifest to match current file hashes. Only run this after changes that
were deliberately approved (e.g. post-HARNESS-UPDATE-APPROVED commit).

## View audit log

```bash
ls -lt ~/.espalier/audit/ | head -20
cat $(ls -t ~/.espalier/audit/*.log | head -1)
```

Shows the most recent audit events written by `session_start.py`.

## When to run

- After any edit to a hash-pinned harness file
- When `session_start.py` reports integrity drift at session start
- After a `HARNESS-UPDATE-APPROVED` PR lands on main

## Related managed-surface signals

The integrity manifest is the strongest tamper-detection layer (SHA-256 hashes
on hash-pinned files), but two other markers signal "this content was deployed
by `espalier init`, not hand-edited":

- **`.claude/settings.json` `_espalier_managed: true` sentinel**.
  If present, the settings.json was deployed by init and is safe to
  regenerate by re-running `espalier init`. Absence means the settings were
  hand-edited or pre-date the sentinel — review carefully before regenerating.
- **`<!-- espalier:managed - regenerated by `espalier init` ... -->`** marker
  at the top of `.claude/{commands,skills,agents}/*.md`. Files with this
  marker are init-deployed; user-authored siblings without the marker are
  preserved across `espalier init` re-runs.

These markers don't replace the integrity manifest — they signal *origin*,
not *integrity*. A file can carry the espalier:managed marker AND still drift
if hand-edited after deployment; the manifest catches that.

# Quickstart

Go from zero to a governed Claude Code session — about five minutes for the
in-place `init` path, or a focused first session for the recommended
**fusion** path. This guide assumes you have an existing repo and Claude Code
installed.

---

## Install by fusion (recommended)

Espalier installs by **fusion**: a single command builds a *new* repo that
is your project + the harness overlaid at root, leaving your original
untouched. Espalier-Harness is in pre-release; a packaged `pipx` / `pip
install` channel is planned but not yet the install path, so fuse from a
source checkout:

> **On macOS, type `python3`.** Stock macOS ships only `python3`, not a bare
> `python`, so the `python -m …` commands below (including `python -m pip`)
> fail with `command not found` unless you substitute `python3`. (Espalier
> detects and pins the right
> interpreter when it writes your hooks; this only affects these bootstrap
> commands. On Windows the launcher is usually `python`.)

```bash
# 1. Get espalier from source
git clone https://github.com/Mike-Byrne-AI/espalier-harness.git espalier-harness
cd espalier-harness
python -m venv .venv
. .venv/bin/activate          # PowerShell: .\.venv\Scripts\Activate.ps1
python -m pip install -e .   # makes the `espalier` CLI importable from any directory

# 2. Fuse your project with the harness into a NEW repo
python -m espalier fuse /path/to/your/repo --out /path/to/your-repo-governed

# 3. Open the fusion in Claude Code and finish the bootstrap
cd /path/to/your-repo-governed
claude   # run the finish-up steps fuse printed
```

`fuse` does the mechanical bootstrap (copy your git-tracked files,
overlay the engine + hooks + docs, reseed espalier-specific content
empty, then wire it via `init` + `install-ci` + a host-targeted
`fingerprint`). The taste — repurposing the verifier tests, emptying
espalier-pinned scanner registries, re-seeding agent bodies host-generic
— is the first Claude session in the fusion; `fuse` prints that checklist.

## Or: govern your existing repo in place

Prefer not to create a new directory? Install the engine and `init` your
repo directly:

```bash
git clone https://github.com/Mike-Byrne-AI/espalier-harness.git espalier-harness
cd espalier-harness
python -m venv .venv
. .venv/bin/activate          # PowerShell: .\.venv\Scripts\Activate.ps1
python -m pip install -e .

cd /path/to/your/repo
espalier doctor .   # optional: see what Espalier detects (and that init is needed)
espalier init .
```

`init` (run directly, or by `fuse`) analyzes your repo (languages,
frameworks, project structure) and deploys the mechanical enforcement
layer:

- **Hook scripts** in `tools/cc/hooks/` — twelve entry scripts plus
  thirteen helper modules that wire into Claude Code's lifecycle events
- **Settings** in `.claude/settings.json` — hook wiring, permissions,
  and tool allow-lists
- **Skeleton docs** — `CLAUDE.md` (Claude's project instructions) and
  `ESPALIER_MEMORY.md` (durable session knowledge)
- **Reports** in `reports/` — repo fingerprint and harness config

Init deploys the full managed surface — 7 / 17 / 9 (agents / commands
/ skills) — to every repo. Every packaged agent, command, and skill
ships; there is no deploy tier to opt into.

### What if my repo isn't Python?

The mechanical enforcement layer (hooks, governance gates, bypass
corpus, integrity manifest) works identically on any language —
init detects TypeScript, Go, Rust, and polyglot repos and writes the
right `CLAUDE.md` `Languages:` and `test_cmd` fields automatically.

What is Python-flavored today:

- **Scanners** (`espalier scan`, the `/scan` slash command,
  `/preflight`'s scan step) are AST-based and Python-specific. On
  non-Python repos they emit a `[WARN]` line to stderr and a typed
  `skipped_no_python_files` result envelope — they're explicit
  about not applying, not silent.
- **Bundled agents and commands** in `.claude/agents/` and
  `.claude/commands/` are authored from Espalier-Harness's own
  Python codebase. Treat them as starting examples to customize for
  your repo's language and conventions; a templating layer is
  planned. See [`../README.md#honest-scope`](../README.md#honest-scope).

Init preserves what is yours: `.claude/settings.json` and `CLAUDE.md` are
skipped when they already exist (init tells you), a seeded doc you have
edited is left as you left it, and a file whose `espalier:managed` marker
you removed is kept across inits. It does rewrite the rest: a seeded doc you
have not edited is refreshed when the packaged copy changes, and a marked
`.claude/` body or generated `cc/` doc is regenerated on drift, edits
included, unless you drop its marker. The one exception is a
`.claude/settings.json` that is empty (0 bytes or whitespace): it has
nothing to preserve, so init rewrites it in place and says so.

### Choose a settings profile

`espalier init` picks a settings profile that shapes `.claude/settings.json`.
The default is `workflow`; the other choices are `minimal` (read/search
only) and `full` (broad-bash power-user posture). All three keep the
hook layer wired and the deny defaults intact — the difference is the
permissions allow list.

```bash
python -m espalier init --profile minimal .    # read/search only
python -m espalier init --profile workflow .   # default
python -m espalier init --profile full .       # broad bash (advanced)
```

Or set the default per-project in `espalier.toml` at the repo root:

```toml
default_profile = "minimal"
```

The CLI `--profile` flag overrides the file. Settings profiles are
governance defaults, not a security sandbox — see
[`docs/SHARP_EDGES.md`](SHARP_EDGES.md) for the boundary.

The generated `permissions.deny` list covers dangerous Bash shapes only. Reads
of `.env`, `secrets/` and credentials files are denied by `write_guard.py` at
the **hook** layer instead — deliberately not as `Read()` deny rules, because
any `Read()` rule makes Claude Code demand static proof of every Bash command's
read set and raises a permission prompt on the ones it cannot prove, which
neither an allow rule nor `bypassPermissions` can suppress.

## Add to .gitignore

These directories and files are per-machine or per-install runtime
state. The harness regenerates them on demand; do not commit them.

```
# Espalier-Harness runtime -- generated, never committed

.espalier/
.espalier-state/

cc/blueprints/
cc/_cold/
cc/_working_summary.md

*.pyc
.claude/*.new
.claude/*.bak
.claude/*.bak.*
/task-packs/
```
<!-- required-gitignore: END generated region -->

This is the complete set — the same block `init` appends, generated from
the same constant, so pasting it by hand leaves you in the state `init`
would have produced.

The leading slash on `/reports/` is load-bearing. Git matches a pattern
carrying no leading or embedded separator at *any* depth, and `reports`
is a name you may well use yourself — without the slash this would also
exclude your own `src/analytics/reports/`. The `.espalier*` entries stay
unanchored on purpose: that name is the harness's, it cannot collide with
anything of yours, and ignoring it at any depth is the safer default.
`__pycache__/` and `*.pyc` are unanchored for the same reason and matter
more than they look: the hooks are Python, so they compile on first run,
and without those two entries an adopter commits hook bytecode on day one.

Since v0.7.9 `espalier init .` writes these entries to `.gitignore`
automatically. Pass `--no-write-gitignore` if you want to handle
the file by hand instead.

`init` also checks these entries against what your repo already tracks.
If you have committed the path itself — your own `.claude/settings.json`,
say — the entry is **not** written, and init prints the `git rm --cached`
that would hand the path over; ignoring an already-tracked path protects
nothing and leaves it both tracked and ignored, which `git check-ignore`
does not report. If instead you merely share a *directory* with the
harness (your own files under `reports/`), the entry **is** written: git
ignores nothing that is already tracked, so your committed files are
unaffected — only a *new* file you add there won't stage, and `git add -f`
covers that.

## Cloning a repo that already uses Espalier

Because `.claude/settings.json` is per-machine and gitignored (above), it
does **not** travel with a `git clone`. A fresh clone of a governed repo
arrives with the full committed harness surface — agents, commands, skills,
hook scripts — but **zero running hooks** until you wire them on this machine:

```bash
git clone <repo> && cd <repo>
python -m espalier init .     # wire the hooks on this machine
```

Until you run `init`, the slash commands and agents work but the mechanical
hooks (`write_guard`, `plan_guard`, `stop_gate`) are silently inactive. The
warning hooks themselves can't fire to tell you — they're exactly what's
missing — so this step is part of the documented clone-to-governed flow, not a
footnote. When invoked interactively, the `espalier` CLI also nudges you, and
`doctor`/`init` recognize this state as `source_checkout`.

## Verify the install

```bash
python -m espalier doctor .
```

Doctor checks that required files exist, hook wiring points to real
scripts, settings parse cleanly, and no kill-switch patterns are
present. A healthy output (truncated to the most-watched fields)
looks like:

```json
{
  "status": "pass",
  "checks": {
    "audit": {"status": "pass"},
    "diff": {"status": "pass", "fingerprint_changed": false},
    "presence": {"surface_present": true, "surface_missing": false}
  },
  "doc_drift": [],
  "failures": []
}
```

The full output also includes `ownership`, `next_steps`, `info`,
`warnings`, and `recover` / `reflect` / `self_host` sub-checks —
useful when triaging a `warn` or `fail` status.

## Start Claude Code

```bash
claude
```

The `session_start` hook fires automatically and loads repo context.
You'll see:

```
=== Espalier-Harness === Session Start ===
Host: OS=Darwin; python3=yes python=no (python3 only)
Repo:      your-project
Branch:    main
Status:    8 uncommitted changes
Memory:    **Repo:** your-project | **Stack:** python
Blueprint: Auto-started new blueprint session
Surface:   healthy
Integrity: ok
Commands: /status /implement-task /smoke /preflight /commit /handoff
Run /status to verify harness state.
```

The `Host:` line reports what your machine actually has. `Status:` shows the
files `init` just deployed, uncommitted — commit them when you're ready.
`Stack:` is what `init`'s fingerprint detected in your tree (`python` here);
`/analyze` fills in the project-specific layer on top of it — conventions and
footguns — and does not change this line. `Integrity:` is the hash manifest
`init` wrote, re-checked at every session start.

From here, the hooks are active. If you try to use Write or Edit on
a source file without a plan, `plan_guard` blocks it. If you try to
write a protected harness file, `write_guard` blocks it. At session
Stop, `stop_gate` runs a four-gate sequence — pytest (opt-in via
`ESPALIER_STOP_GATE=full`), docs refresh, code review, and blueprint
finalize.

These are all explained in [`HOOKS.md`](HOOKS.md).

## Ground the harness on your repo

`init` deploys the harness and fingerprints your repo, but the

your first Claude session. Run `/analyze`: `repo-analyst` establishes the

still empty. Full sequence (both install paths) in

## Your first change

Try the basic workflow:

```
/implement-task Add a greeting message to the main function
```

Claude will present a plan and wait for your approval. After you
approve, it creates an execution plan, makes the change, runs the
targeted test, and reports results. This is the standard loop for
every change.

## Customize plan_guard for your source layout (optional)

By default, plan_guard requires an active execution plan before any
`Write` or `Edit` to source files. The default exempt list covers
the harness's own internals (`tests/`, `tools/cc/`, `.claude/`,
`cc/`, `reports/`, `memory/`, `docs/`, `task-packs/`, `.espalier-state/`) but **not** conventional source roots like
`src/` or `lib/`. For tiny edits (a typo, a type annotation), the
plan-required ceremony can feel heavy.

Add an opt-in exemption in `espalier.toml` at the repo root:

```toml
# espalier.toml
plan_exempt_prefixes = ["src/", "lib/"]
```

Now `Write`/`Edit` on paths under `src/` or `lib/` skip the plan
requirement. Each entry must end with `/`; absolute paths and `..`
traversal are rejected (any invalid entry drops the whole list
into strict mode and writes a `[plan_guard]` advisory to stderr).

**Do not use `ESPALIER_MAINTENANCE_MODE=1` for this purpose.** That
env var bypasses `plan_guard` and also `write_guard`'s protected-zone check,
two of `stop_gate`'s gates and `subagent_stop`'s blueprint append — it is scoped for harness self-edits, not
adopter ergonomics. The `plan_exempt_prefixes` knob is the
narrow, explicit alternative. See
[`docs/sharp-edges/plan-guard-adopter-source-roots.md`](sharp-edges/plan-guard-adopter-source-roots.md).

## Enable CI enforcement (optional)

The hooks are local friction — they raise the cost of mistakes but
can be bypassed. For a real guarantee, add the CI gate:

```bash
python -m espalier install-ci .
```

This deploys a GitHub Actions workflow that fails the build if any
committed file contains a kill-switch setting (`disableAllHooks`,
`bypassPermissions`, empty hook lists). Combined with branch
protection (require the status check to pass before merging), this is
the guarantee layer. See [`INSTALL-CI.md`](INSTALL-CI.md)
for the one-step setup.

## Uninstalling

If you want to remove Espalier from your repo cleanly:

```bash
# Preview what would be removed (dry run, no changes)
python -m espalier clean-generated .

# Actually remove all harness-deployed files
python -m espalier clean-generated . --execute
```

This removes every file carrying the `espalier:managed` marker — the hook
scripts under `tools/cc/`, the `.claude/` agents, commands and skills, the
generated `cc/` docs — plus the bytecode caches under them, and strips what
`init` or the merge wrote into `.claude/settings.json`: the hook entries, its
`statusLine` and its managed marker (your own keys stay). It preserves, and
names in its report, everything else it wrote: the seeded docs (unmarked,
so you can edit them), `settings.json` itself, the runtime state under
`.espalier/`, `reports/` and `cc/blueprints/`, and any `settings.json.bak`
a merge took. The `.gitignore` entries it appended are retired one by one
as nothing needs them; an entry still guarding a preserved file stays, and
the report lists both. Files you authored yourself are never touched.

After cleaning, if you installed espalier as a package (`pip install
espalier-harness`), uninstall that separately. If you **fused** from a source
checkout — the current install path — there is no installed package to remove;
deleting the espalier clone is enough.

```bash
python -m pip uninstall espalier-harness   # only if you pip-installed espalier
```

## Upgrading

When you bump the engine (`git pull` in the espalier checkout, or a future
`pip install --upgrade`), re-deploy your committed harness in place:

```bash
# Preview what would change (dry run, no writes) -- the default
python -m espalier upgrade .

# Apply: re-deploy managed assets, merge hook settings, refresh integrity
python -m espalier upgrade . --execute
```

`upgrade` reads the version stamped into `cc/PACK_MANIFEST.txt` at deploy time
and diffs it against the engine you're running -- and because a version string
can stand still across many engine commits, it also compares the deployed
hook and tool scripts, the agent, command and skill bodies, and the cc/
surface docs against what the engine would write, and the saved plan
(`reports/harness_config.json`) against the tree, so a hook altered in place,
a deploy that fell behind the engine, or a retired agent still listed is named
in the preview instead of read as current. On `--execute` it re-deploys the
managed assets, re-baselines the saved plan (regenerated from the
fingerprint; hand edits to it are replaced, `settings_profile` is kept), runs
`merge-settings` on your
`.claude/settings.json` (preserving your keys; keeping a `.bak` of them), surfaces any
retired managed files, and refreshes the integrity manifest. Permissions stay
yours: `upgrade` appends hook events and adds espalier's `statusLine` when
that key is absent (a `statusLine` of your own is never touched), and in both
modes -- including when the harness is already current -- it
names any allow rules of your install's profile that the file lacks;
`python -m espalier merge-settings . --add-allows` appends those after your
own rules, never removing one and never touching a rule you denied or set to
ask; `doctor` reports the same gap. (`init` records which profile it rendered
your file from in `reports/harness_config.json`, so the comparison is against
that profile, not a default.) Your hand-authored `ESPALIER_MEMORY.md`, `CLAUDE.md`, convention
guides, and sharp-edges notes are **never** rewritten.

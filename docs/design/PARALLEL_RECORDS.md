## 2. Diagnosis

Four files every lane rewrites, with stored totals and a shared append anchor.
The conflicts are almost never two agents disagreeing about work; they are two
agents recomputing the same totals or appending at the same line. That is a
data-layout problem. Merge tooling treats the symptom, and this repository
already has more of it than any human team ever built.

How teams of hundreds avoided it: the bug tracker was never in the source
tree; changelogs went to one-file-per-change fragments assembled at release;
OWNERS files partitioned the tree so parallel work rarely met in a file; a
merge queue serialised landing; and a person resolved a same-file add/add in a
minute without a tool.

## 3. Where air agrees with win

- **Ownership through a dispatcher.** A dispatcher handing each machine a
  non-overlapping file set is ownership by construction. The mail claims
  already express it; a live board shows it.
- **Changelog fragments.** One file per change (towncrier's shape), assembled
  at release. `CHANGELOG.md` conflicted in 10 of the 30 replayed catch-ups,
  and no server honours `merge=union`.
- **A board instead of mail for state.** "What is open, who holds what, which
  pull request blocks which" is a derived read model and belongs in one.

## 4. Where air differs: the ledger's rows stay in the tree

The operator asked whether the probing, classification, ordering and the
sister-site sweep still work with the ledger in an external database. Mostly
not, because the ledger's proof layer is bound to a commit:

- A probe is a one-liner run against the checkout at a commit;
  `check_ledger_probes.py` and `ci_guard.py` read the roster from the tree.
- A strike rides the commit that fixes it: the pull request proves its own
  row. `scripts/check_handoff_landing.py` pins row shas against the tree.
- `tests/test_forward_ledger_completeness.py` cross-checks every pack against
  the ledger's id set. Readers today, measured by grep: 18 tools, scripts and
  engine modules (`espalier/cli.py`, `managed_inventory.py`,
  `provenance_census.py`, `surface_contract.py`, the subprocess scanner,
  `ci_guard.py`, `generate_ledger_regions.py`, `ledger_row.py`,
  `record_merge.py`, `check_ledger_probes.py`, two hook helpers, six
  scripts) and 34 test files.
- The ledger is seeded to adopters (`espalier/assets/seed/FORWARD_LEDGER.md`)
  and `scripts/ledger_trend.py` walks its history on the orphan `record` ref.
- `sister_site_probe.py` does not read the ledger at all (it is name-keyed
  over source), so it is unaffected either way.

An external database can hold all of this, but every reader above is
rewritten and a pull request can no longer carry its own row. The database
belongs on the read side (5C).

## 5. The combination

**A. Write fragments to the tree.** Each record is its own file: a ledger
row, a session's memory row, a changelog entry. Two lanes adding two files
never conflict. The big files become views. The fork to settle with win: a
*committed* view (regenerated by a job on main after each merge; lanes never
touch it, but a lane's tests read a view that is stale until main
regenerates) versus a *loader* (readers assemble the view from fragments on
demand; no hot file at all; 18 readers and 34 tests move to one helper). The
up-to-date rule can only return hand-free under the loader, or under a view
that only main writes.

**B. Ids without coordination.** A content hash (the probes already carry
`row_sha` and `text_sha`) or a machine prefix. With fragments a duplicate
becomes an add/add on the filename: visible, never silent. Interim, about an
hour in `ledger_row.py file` once win-2's claim clears: mint from the maximum
over `origin/main` and every `origin/lane/*` head, not the local maximum.
That is exactly how `DEF-1197` happened: win's claim was released at ship,
the id lived only in an open pull request's diff, and the live-claims check
saw nothing.

**C. Read from a derived board.** Counts, trends, claims, assignment,
"blocked on which PR": built from main after each merge. The dispatcher reads
it; nobody edits it. This is win's database, placed where it does no harm.

**D. The up-to-date rule.** With clean server merges, `gh pr update-branch`
works and the rule costs no hand step. Its remaining cost is one CI run per
catch-up (the 1.8x). The merge queue is unavailable on a personal account
(TP-478 0-C), so the rule is the poor man's queue. Recommendation: back on
after step 3 below, if the operator wants pre-merge proof of the merged
result over CI minutes.

**E. What stays hand work.** Two lanes editing the same source or test file
(1 of 30). The dispatcher's partition shrinks it; `record_merge.py` gains a
`--continue` mode (a merge in progress, every remaining unmerged path on the
roster: resolve and commit), so a one-file hand resolve lets the rest finish
mechanically. Both of today's merges would have finished that way. Its
refusal text today names a renumber verb that `ledger_row.py` does not have
(verbs: strike, class, file, repin).

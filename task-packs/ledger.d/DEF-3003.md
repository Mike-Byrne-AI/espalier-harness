| `DEF-3003` | espalier/cli.py::_file_onboarding_rows (files only into an untouched seed ledger); espalier/cli.py::cmd_upgrade (never rewrites a filed onboarding probe) | **An adopter who installed before a release that changes an onboarding probe keeps the old probe in `task-packs/LEDGER_PROBES.json` through every `upgrade`, so a fix to how an onboarding row reads its file never reaches them.** `espalier/cli.py::_file_onboarding_rows` files the rows only while the forward ledger is the untouched seed, and `espalier/cli.py::cmd_upgrade` has no step that compares a filed row's stored probe with the engine's code in `espalier/cli.py::_ONBOARDING_ROWS`. Who is hurt: an adopter who ran `init` between the forward ledger's first release (2026-09-30) and the onboarding lane (2026-10-11), then writes their goal into `cc/GOAL.md` as row ONB-1 asks: their ONB-1 keeps the whole-file test, so it reads open until a `/handoff` fills the next section (the `DEF-1032` symptom), reads closed when they opt out but keep the file (`DEF-1033`), and is UNRESOLVED on a goal saved as UTF-16 (`DEF-1034`); ONB-6 and ONB-7 keep their strict reads the same way. Reach not measured: the population is every install in that window. Found 2026-10-11 at the onboarding lane's Task 0, by reading the filing path, and driven: `init` on a temp tree, one character of the stored ONB-1 probe changed, the deployed stamp in `cc/PACK_MANIFEST.txt` set to `0.0.1`, `upgrade --execute` (exit 0, the re-deploy path ran), the changed probe still stored. Fix shape (untested): on `upgrade --execute`, rewrite each live onboarding row's stored probe (the ids `_ONBOARDING_ROWS` names, derived, never a list of known old codes) whose command differs from the engine's, name each one in the report, and leave a row the adopter struck or deleted as they left it. The probe drives exactly that sequence and prints whether the stored ONB-1 probe still differs from the one `init` filed: True while open. | minor |

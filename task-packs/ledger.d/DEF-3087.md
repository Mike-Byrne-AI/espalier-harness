| `DEF-3087` | tools/cc/hooks/session_start.py::_warn_if_nested_repo_litter (never names git worktree repair for a worktree whose links a repository folder move left dangling) | **After the repository folder moves, SessionStart's nested-repo warning never names `git worktree repair` for a worktree under it whose links now dangle.** git records a linked worktree by absolute path in both directions (the worktree's `.git` file and `.git/worktrees/<id>/gitdir`), so moving the repository folder leaves each worktree inside it broken: git run in it fails, and `git worktree list` names its old path, prunable. `tools/cc/hooks/session_start.py::_warn_if_nested_repo_litter` then says one of two wrong things. Driven 2026-11-15 on the Windows box (git 2.52.0.windows.1) at origin/main 13727ef, a repository with a worktree at `.claude/worktrees/2` moved by rename: with nothing else untracked beside it the line is silent (git status is blind to a dangling gitlink, and source A skips the old path, whose folder is gone); with another untracked file in `.claude/` it names the worktree as a nested git repo the registry does not list, with `move it out of the working tree ... or add it to .gitignore`, because the on-disk registry read (`tools/cc/hooks/_hook_utils.py::sibling_checkouts`) skips a registration whose recorded folder is gone. Neither says the remedy, `git worktree repair <path>` run from the moved checkout, which rewrites both links (measured the same day: rc 0, and git runs in the worktree again). The reaper does not reach it either: `tools/cc/checkout_sync.py::_reap` judges registrations under the current `.claude/worktrees/` alone, and the old path is not under it (it does refuse the repository-wide `git worktree prune` while such a registration stands, which would drop the record a repair needs). Who is hurt: an operator who moves the repository folder (this operator's folders move often), whose `--worktree` sessions' checkouts stop working while the banner says nothing, or says to move or ignore them; a `git worktree prune` run on the advice of any prunable listing then drops the records and the repair with them (measured: after a prune the repair exits 1, `.git file does not reference a repository`, and the worktree stays broken). A second shape of the same read, unmeasured: a registry past `_hook_utils._REGISTRY_ENTRY_CAP` (256) entries sorts a real worktree as a nested repo. Lead 3 of note e72e1b (DEF-5109's reviews), left by DEF-3086's lane because the dry run that lane names cannot see it. The fix needs its own oracle: telling a moved repository's worktree from a foreign clone without a spawn per entry under the wall (a gitlink naming `<old root>/.git/worktrees/<id>` where this repository's registry holds `<id>`). The probe drives the line on a temporary repository moved by rename with its worktree inside and prints whether it fails to name `git worktree repair`. | minor | LOGIC_BUG | ADOPTER |

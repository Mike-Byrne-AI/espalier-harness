| `DEF-3092` | tools/cc/hooks/config_guard.py (settings-unreadable say_once: configchange_failed_open_settings_read) | **config_guard skips its kill-switch scan of a settings file about once a session on the Windows box, and its record does not say which file.** `tools/cc/hooks/config_guard.py` reads the changed settings file on each ConfigChange; a read that raises (`json.JSONDecodeError` here) fails open with voice as `configchange_failed_open_settings_read`, once a session, and the change passes unjudged. The Windows box's audit logs hold 77 such records in November across the main checkout and worktree `2`, on 13 of 14 logged days (counted 2026-11-16 by the failure-mode review of DEF-1152's lane; this seat's census the same day read 1 to 11 a day in the main checkout). The cause is probably the read landing mid-write of Claude Code's own settings save (not confirmed), and the record's `details` carry the key and the fault, not the file's label. Who is hurt: the operator whose settings change carrying a kill switch is the one read torn: the scan of that file is skipped and the switch lands, with one record a session as the trace (which the next SessionStart now names). Fix shape: read the file once more after a short wait when the parse fails (a torn write settles), judge what that read holds, and name the file by label in the record; the record then means a file that stayed unreadable. No probe: the fault is a race with Claude Code's own write, which a one-liner cannot drive on demand; the census of `configchange_failed_open_settings_read` per day in `~/.espalier/audit/` is the measure. | minor |

It is the one guard that judges by state rather than by parsing the command, so it caught a write the action parser never judged (2026-10-12, lane/audience-gate: a Python byte-replace on `espalier/cli.py`). The same session showed the other half: `write_guard`'s start-time helper-skew refusal denied every tool call, the shell included, until a human edited the file from a terminal, because a deny that judges nothing leaves no spelling to get around. Who is hurt: an unattended run (a `/loop`, a scheduled or headless agent, an adopter tree without `install-ci`) where nobody reads the advisory; the run continues until the next SessionStart reports integrity drift, or a merge gate where one is installed. Fix shape (untested): on an unaccounted change the after-check writes a latch, `write_guard` refuses every call while it is set, and only a human clears it from a terminal (the lock protects its own release). Measure first: read a month of the after-check's audit records and classify each firing as legitimate or unwanted against a bar set before looking, because a latch on noisy detection is worse than none (the firing that motivated this row was legitimate maintenance-mode work); if it passes, latch unattended runs first and keep the advisory in interactive ones. Limits, so the row is not read as a boundary: detection follows the action, so one irreversible act gets through; a read leaves no state to detect (the read-side analog, a canary token caught in PostToolUse output, catches a naive read into the transcript and nothing transformed); and a command that rewrites both a file and its baseline defeats it.

| ~~`DEF-1106`~~ | espalier/cli.py::gitignore_status; espalier/doctor.py (required .gitignore entries missing, a re-init is safe); espalier/cli.py::_handle_gitignore | ✅ **CLOSED 2026-10-05 — `espalier.toml` takes `gitignore_declined` (a `HarnessConfig` field) read only by `config.declined_gitignore_entries`, which every command passes from the configuration it loaded, so `--config` is honoured; `cli.gitignore_status(repo_root, *, declined=None)` leaves a declined required entry out of `missing`, `unanchored` and `withheld` and reports it in `declined` (a value that is not a required entry in `declined_unknown`), so init's append and both `upgrade` arms, through `_handle_gitignore`, never write it, and `doctor` lists it as information, warns on an unknown value, and for a missing open-set entry says files there stop staging instead of calling a re-init safe. Documented in `docs/CONVENTIONS.md`. Pinned by `tests/test_init_gitignore_default.py::TestAnAdopterCanDeclineARequiredEntry`, `tests/test_doctor.py::TestDoctorHonoursADeclinedGitignoreEntry` and the doctor warning-site census, all red on the unfixed tree. Not done: the optional advisory listing untracked packs a rule hides.** PRIOR TEXT: **An adopter cannot decline a single `.gitignore` entry the harness requires: `gitignore_status` takes no configuration, so a dropped entry comes back as missing, and `doctor` prescribes a re-init (`a re-init is safe`) that puts it back.** `espalier/cli.py::gitignore_status` is a pure function of the repo root and the tracked files; the only opt-out is the whole-block `init --no-write-gitignore`, and `upgrade --execute` calls `_handle_gitignore` with no such flag. An entry the adopter removed on purpose is therefore reported missing by every run, `espalier/doctor.py` lists it as an actionable warning, and the remedy text it prints re-applies the declined entry. The case that made this costly was `/task-packs/*` on a repo that already versions its own packs: the open-set test `_entry_covers_an_open_set` filed it as `shared` and wrote it over tracked content, so every new pack silently stopped staging. Found by the 2026-10-03 adoption audit (`espalier-issues/audits/2026-10-03-adoption/public_report.md`, C-12); re-checked at `08ab2db`: PARTLY-FIXED: `a50c173` added `AUTHORED_OPEN_SETS`, so `/task-packs/*` is no longer written over a folder the repo already commits into, and init, doctor and upgrade now name the rule to delete and the files it would unhide. What did not land: a per-entry decline, and any surface that lists untracked packs the rule hides on a repo that tracked none at install (the rule is then written by design). The audit's count was measured on one adopter with a prior harness. Who is hurt: an adopter who removes one entry from the managed block to keep a folder tracked, and then gets a permanent doctor warning whose prescribed fix undoes the removal. Fix shape: an additive `espalier.toml` list of declined entries (for example `gitignore_declined`) that `gitignore_status`, `_handle_gitignore`, `doctor` and `upgrade` all honour, with the doctor remedy for an open-set entry stating its consequence rather than calling the re-init safe; optionally an advisory that lists `git ls-files --others --ignored` paths under `task-packs/` so a hidden pack is never silent. | minor | LOGIC_BUG | ADOPTER |

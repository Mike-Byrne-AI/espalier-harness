| `DEF-4106` | tools/cc/board.py::read_post_merge (a completed cancelled run is neither a verdict nor going) | **The board's base line reads a post-merge run that ended cancelled as nothing at all, so main reads proven on an older green while the merges after it have no verdict.** `tools/cc/board.py::read_post_merge` walks the runs newest first: a completed run concluding `SUCCESS` sets the verdict and stops, one in `tools/cc/_post_merge.py::RUN_RED` (failure, timed out, startup failure) sets red, and any other completed conclusion, `CANCELLED` among them, is skipped and leaves no trace in the result, neither a red nor `running`. A job cut by its `timeout-minutes` concludes cancelled, and `.github/workflows/post-merge.yml` sets no `cancel-in-progress`, so a cancelled run there is a cut or a hand cancel, never a superseded one. Run 42614778252 (the full tier, cancelled 12:10:24Z to 13:26:23Z on 2026-11-09): from 13:26Z to 13:37Z the line read green on 4161eac with nothing going, while #549 and #550 had no verdict (derived from the code and the run list, not read on a board at that minute). The base-run reader for the advisory push workflows, `tools/cc/_post_merge.py::base_run_verdict`, already names a cancelled run newer than a green, so this is the one sister site that does not. Who is hurt: the dispatcher deciding revert-first, and a seat arming onto main, each reading main as proven past merges no run judged; the suspects stay right, since they run from the last green, so the cost is a late proof, not a wrong revert. Fix shape: name each cancelled run newer than the last green by sha and run id, say that main is unproven past them, and carry the same in the JSON.

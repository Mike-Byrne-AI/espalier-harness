| `DEF-1104` | espalier/cli.py::cmd_upgrade; espalier/cli.py::cmd_init; espalier/cli.py::_read_deployed_version; espalier/render_surface.py (PACK_MANIFEST version stamp) | **`upgrade` and `init` cannot tell which side is newer: an older installed engine rolls a tree deployed by a newer build back to its own bytes, reports it as repairing drift, and re-seeds the integrity manifest over the result.** The engine stamps only `# espalier-version: <__version__>` in the pack manifest, and a pre-release string does not move between merges, so two builds share one version. `espalier/cli.py::cmd_upgrade` compares the deployed stamp to the engine by equality alone (`deployed_version == __version__`). On the same-version arm the content oracles compare the tree to the installed engine's packaged bytes and present every difference as `the deployed surface is not current`; on the different-version arm it prints `deployed X -> engine Y` and proceeds even when X is the later one. `cmd_init` never reads the stamp. `upgrade --execute` and `init` then overwrite every marked hook, tool and `.claude` body that differs and rewrite untouched seed docs to the older body, and the integrity manifest is re-written over the result, so `integrity verify` is clean and the git diff looks like a routine refresh. Managed hooks are normally committed, so one run from a lagging install can revert guard fixes in a shared tree, recoverable only through git. Found by the 2026-10-03 adoption audit (`espalier-issues/audits/2026-10-03-adoption/public_report.md`, C-10); re-checked at `08ab2db`: LIVE (equality-only compare re-read at HEAD; the audit's rollback was observed on one adopter with two machines). Who is hurt: an adopter on two machines or a team with mixed installs whose older install runs `init` or `upgrade --execute` and quietly reverts newer guard code. Fix shape: stamp a build identity (a digest of the packaged managed surface, plus the VCS commit from the install metadata when present) next to the version; add a stdlib version-ordering compare (`packaging` is not a runtime dependency); when the deployed side is newer, or the version matches and the build differs or is unknown, say so instead of `not current`, and make `upgrade --execute` and `init` refuse managed overwrites without an explicit override while naming the files they would rewrite; have `init` read the stamp before deploying. Ordering half landed 2026-10-10 (the upgrade lane, `lane/upgrade`, `espalier/cli.py::_deployed_is_newer`): a deployed stamp that orders after the engine refuses `upgrade`, `init`, `install-ci` and `fingerprint` in both modes before any write, naming the files they would roll back; a stamp it cannot parse never refuses, and deleting the stamp line is the named way past. Still open: two builds of one pre-release string compare equal, so the build identity beside the version is the remainder (the probe watches for it), and the explicit override the fix shape names was not built. | minor | LOGIC_BUG | ADOPTER |

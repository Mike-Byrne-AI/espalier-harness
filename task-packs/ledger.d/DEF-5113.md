| `DEF-5113` | espalier/cli.py::cmd_init (records the --profile flag's profile over a settings file the deploy keeps); espalier/cli.py::installed_settings_profile (every later reader) | **An `init --profile <name>` re-run over an existing `.claude/settings.json` records `<name>` as the profile that file was rendered from, though it keeps the file and renders the new profile only into `settings.json.new`, so every later reader judges the kept file by a profile it was never rendered from.** `espalier/cli.py::cmd_init` writes `settings_profile` to `reports/harness_config.json` from the `--profile` flag (else `espalier.toml`'s `default_profile`, else the record, since `DEF-2004`) before the deploy, and on a re-run the deploy keeps the existing file (`::_reconcile_existing_settings`, case (a)) and renders the flag's profile beside it. `::installed_settings_profile` then hands the flag's profile to every later reader (`doctor`, the `upgrade` reports, `merge-settings`), whose comparisons take the record to be the profile the file was rendered from, as `DEF-2004`'s closure says it is. Driven 2026-11-15 on a scratch Node tree (the `DEF-1155` failure-mode review's second warning): a workflow `init`, `Bash(npm *)` planted, then `init --profile minimal`. The file was kept (12 allow rules, `Write` among them) and `settings.json.new` rendered; the re-run itself named the broad rule, since it judges by the record it read before its own write (`DEF-1155`), but afterwards the record read `minimal`, and `doctor` and `merge-settings` named neither the broad rule nor any allow-rule difference: the minimal profile derives nothing from the fingerprint, and its three rules are all present. Who is hurt: an adopter who re-runs `init --profile minimal .` to move a workflow install to the read-only posture, does not adopt the `.new` file, and is told by every later `doctor` run that nothing about the allow list needs attention while the file still pre-approves `Write` and any broad rule an older init wrote. Fix shape (untested): when the deploy keeps an existing file, keep the record at the profile that file was rendered from and say the asked-for profile is in `settings.json.new` (recorded once the operator adopts it, or by `merge-settings --profile`), or record both.

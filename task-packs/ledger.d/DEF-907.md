| `DEF-907` | bench/run_benchmark.py::main (the `--baseline` filter); bench/run_benchmark.py::summarize; bench/run_benchmark.py::render_report; published consumer bench/README.md (the one-baseline invocation) | **A benchmark run filtered with `--baseline` writes a report that states measured zero-scores for baselines it never executed.** `bench/run_benchmark.py::main` honours the filter only when choosing what to run (`baselines = args.baseline if args.baseline else BASELINES`), then calls `::summarize` and `::render_report`, both of which iterate the module-level `BASELINES` constant, and writes the per-run `<timestamp>-report.md` unconditionally; the console tail skips an un-run baseline, so the terminal is right and the file that outlives the run is wrong. Driven at HEAD with results for `espalier` alone: the Baseline table prints 0 / 370 in-scope and 0 / 13 out-of-scope for the three absent baselines, where canonical `bench/RESULTS.md` records 13/13 out-of-scope for each and 1/370 for `minimal-hooks`; the per-class detail table repeats the fabrication across all 65 rows. The inverse filter renders `espalier` at 0 / 370 blocked, reading as a total regression of the property the bench exists to prove; `--update-canonical` is protected, so only the per-run artifact lies. Who is hurt: a maintainer running the one-baseline invocation `bench/README.md` and the module docstring publish as supported, who reads the timestamped report README points at and takes a skipped baseline's zero for a measurement. Fix shape: thread the executed `baselines` list through `summarize` and `render_report` and iterate it instead of the constant -- the same edit reaches the detail table and the totals `render_report` reads from `BASELINES[0]` -- or render an un-run baseline as not run rather than as a zero. The probe keys on `summarize` and `render_report` still iterating the global `BASELINES`; the not-run variant keeps that iteration and re-pins the row.

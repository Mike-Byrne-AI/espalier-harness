| `DEF-5084` | tools/cc/board.py::base_run_workflows (the roster reads the checkout's workflow files, not the base's) | **The board's base-run roster is derived from the checkout's workflow files, not the base's, so a push workflow newly merged to the base is read by no seat until that seat's checkout catches up.** `tools/cc/board.py::base_run_workflows` lists `.github/workflows/` in the working tree, while the same board has already fetched `origin/<base>` and reads its ledger count from there for this reason (`read_ledger_at_base`). A seat's checkout moves at its SessionStart catch-up or its next lane branch, and the dispatcher's main checkout reads the board every fifteen minutes between them, so a workflow that lands on main mid-window, and reds there, shows on no line in that window: DEF-5083's gap, for that one workflow and for hours. A workflow a lane deletes is the converse: the lane's own board stops reading it. Found by the failure-mode review of DEF-5083's lane, declared in `base_run_workflows`'s docstring there. Fix shape: list and read the workflow files at `origin/<base>` (`git ls-tree`, then `git show` per file, or one `git archive` as the ledger read takes), the checkout's files the fallback where the clone has no such ref, the board tests' runner taught the two git reads. Who is hurt: the dispatcher and the worker seats reading `/inbox board` before stating state, after a merge that adds or renames a push workflow on main. Probe: whether the roster's reader names the base's ref at all. | minor | LOGIC_BUG | MAINTAINER |

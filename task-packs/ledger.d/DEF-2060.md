Every `-m espalier ...` remedy built on `_remedy_interpreter` or `_remedy_py` then opens with `"<path with a space>"`; the engine has 114 such call sites in `cli.py`, `doctor.py` and `fuse.py`. Driven on Windows 11 with this checkout's own spaced `.venv\Scripts\python.exe`: cmd and Git Bash run a quoted program word, but Windows PowerShell 5.1 refuses the line as a parse error. PowerShell's call operator, `& "<path>"`, runs there and is a syntax error in Git Bash, so no single spelling serves all three shells. DEF-929's dot head (DEF-3017) works only for a file the shell itself runs, never for a command the reader types. Who is hurt: a Windows adopter whose only good Python has a space in its path (a venv in a spaced user folder, `C:\Program Files\...`), whose PATH `python` is a Store alias or below the floor, and who pastes the remedy into PowerShell, the default Windows terminal. They get a parse error instead of the repair. The argument slots after the interpreter are quoted correctly since DEF-912; only the program word is affected. The same quoted spaced head is what `espalier/cli.py::_swap_interpreter_token` writes into a shell-form hook command (DEF-4094), whose docstring says that hook runs in PowerShell where Git Bash is absent; that reach is read, not driven. The fix shape is open, so it is not fixed here: name both spellings, print the remedy in the reader's shell when it can be known, or prefer a launcher spelling (`py -3`) that needs no quoting.

Three call sites exist at HEAD -- `tools/cc/hooks/_hook_utils.py::_project_root_spelling`, `::_clean_path_prefixes` and `tools/cc/hooks/_bash_patterns.py::_posix` -- the rule is written into `docs/SHARP_EDGES.md#Path Normalization on Windows`, and nothing fires when a fourth site appears without the call: `tools/cc/sister_site_probe.py` is name-keyed, so a normaliser that merely omits the call duplicates nothing; no census enumerates these functions; and no `# msys-drive: ok` annotation exists anywhere in the tree. Who: a Windows adopter in Git Bash on the day a new normaliser lands without the call, with no test to say so. Fix: an AST scan over `tools/cc/**/*.py` -- not `tools/cc/hooks/*.py` -- for a function that calls `os.path.realpath`, `.resolve()` or `.relative_to()` on a parameter, requiring either a `_msys_drive_to_windows` call in the same function or a `# msys-drive: ok <reason>` annotation, seeded with the three sites plus `tools/cc/hooks/config_guard.py::_scan_payload`, which fails safe on the spelling and says so inline.

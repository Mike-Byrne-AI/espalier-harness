| `DEF-5101` | tools/cc/hooks/_speedbump.py::_pred_mcp_sideeffect (steps aside only on six top-level _LOCAL_FS_FIELDS keys) | **The MCP side-effect speed bump tells a local filesystem move that it "leaves the repo" whenever the move names its paths under keys other than six top-level local fields, nested or not.** `tools/cc/hooks/_speedbump.py::_pred_mcp_sideeffect` steps aside for a local filesystem tool only when one of `_LOCAL_FS_FIELDS` (`path`, `file_path`, `destination`, `new_path`, `src`, `dst`) is a top-level key with a value; it never reads values or nesting. So `move_file` with `from` and `to`, with `source` and `to`, or with a batch of moves under any key reads as an external side effect, and `CP-MCP-SIDEEFFECT` refuses it once per tool with its body ("an external side effect (send/delete/trigger) that leaves the repo and may be irreversible"), a false statement for a move inside the checkout. Driven 2026-11-10 at 07685c0: top-level `from`/`to` and a nested `moves` list both fire, and the control with `path`/`new_path` stays silent. Found by the failure-mode review of DEF-2026's lane, where the new test class's nested `from`/`to` cells reached the bump end to end; the dispatcher widened it from nested moves to any move without those six keys (air's ruling 0ab7e6). It is message text on a kept job (the speed bumps), a keep class under ruling c825b4.  Who is hurt: an adopter whose MCP filesystem server names a move's paths `from`/`to` (or batches them), nudged once per tool with a text that says the call leaves the repo when it does not.  Fix shape: read the local-filesystem defer from what the tool does (a move or rename action whose path-shaped leaves resolve inside the checkout, through the leaf walk), not from six top-level key names; no spelling list.  The probe drives the predicate on the two firing shapes and the silent control. | minor | LOGIC_BUG | ADOPTER |

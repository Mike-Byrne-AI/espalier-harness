Under the Workflow API a skipped agent or a subagent that dies on a terminal error resolves to `null`, and a thrown lane becomes `null` under `parallel()` and `pipeline()`, so a clean-empty lane, a skipped lane and a failed lane are all `[]`. Nothing counts them: `_fanout_audit.js` and `_layered_review.js` return a static `findersRun` beside `candidates = 0`, `_layered_review.js` returns early with no persist when everything is empty, and the lane tags are stripped before persist, so the per-run ledger leaves no trace of a lane that returned nothing. The convergence template's terminal critic may write `converged` only if a corpus-blind pass produced a null, but it has no data to check that precondition against, and it appends a durable row to the tracked `memory/CONVERGENCE_LEDGER.md`, which the recall index reads. This contradicts the repo's own canon that a probe's silence is not a null. Swapping `.catch(() => [])` for an error object alone would miss the `null`-return path, which is probably the commoner failure. Found by the 2026-10-03 adoption audit (`espalier-issues/audits/2026-10-03-adoption/public_report.md`, C-6); re-checked at `08ab2db`: LIVE (mechanism read in all three bodies at HEAD; no run was observed).

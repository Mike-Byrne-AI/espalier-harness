| `DEF-4113` | tools/cc/checkout_sync.py::_pid_reused (Windows only, so a reused pid reads live off Windows) | **`tools/cc/checkout_sync.py::_pid_reused` compares a registry entry's `procStart` with the process now holding its pid on Windows alone, so on macOS a crashed session's stale entry whose pid another process now holds reads as a live session, and the chain watch #591 landed excuses a test's chain write on that reading.** The function returns False unless `os.name` is `nt` and `procStart` is all digits (its docstring: "Windows only (the field is measured there)"), and `tools/cc/checkout_sync.py::live_sessions` keeps an entry unless `pid_alive` reads False or `_pid_reused` reads True. On this Mac the field is there to compare: the entries under `~/.claude/sessions/` carry `procStart` as `ps -o lstart` text in UTC (`Sat Nov  7 02:09:01 2026` for a pid whose `TZ=UTC ps -o lstart=` prints the same, read 2026-11-11; local `ps` reads five hours earlier); Linux is unmeasured. docs/HOOK_ASSUMPTIONS.md (Assumption 6) declares a recycled pid "the one silent wrong answer left" and names only the worktree reaper, where it fails safe (a worktree kept). Since #591, `tests/conftest.py::_live_chain_owner` reads the same `live_sessions`, and there it fails open: a stale entry placed in this checkout lets a chain move through with a warning. The other readers read fail safe, change only words, or are unread: the catch-up holds; `tools/cc/seat.py::_refuse_occupied` and `::cmd_retire` refuse or keep; the box lock asks on the mail instead of offering a stop; `tools/cc/ship.py::shared_checkout`, `tools/cc/hooks/_speedbump.py::_kill_reading` and the board's `seats:` line name a session that is gone; `tools/cc/ship.py::own_clear_checkout` finds its entry by session id, then by an ancestor's pid, so a reused ancestor pid could place the own-clear in another checkout (probable, not driven). Driven at 9a6eec1: `_pid_reused(<the probe's own pid>, {"procStart": "Thu Jan  1 00:00:00 2026"})` returns False on this Mac. Who is hurt: the maintainer whose checkout's last session crashed, leaving its entry, and whose test then leaks a chain write once that pid is reused; the run warns and passes, and the red arrives a CI cell later. No sighting: it takes a crash, a reuse and a leak, shown as a mechanism only. Fix shape: off Windows, read the pid's start with `ps -o lstart= -p <pid>` under `TZ=UTC`, bounded, compare it with a text `procStart`, and keep False wherever either cannot be read; a comparison in local time would read every live entry as reused, and the reaper would then remove worktrees a session works in. Name the chain watch in the Assumption 6 sentence. Ruled a row by air (note 29bba8). The probe asks `_pid_reused` about its own pid twice, with a January start and with its true start (`TZ=UTC ps -o lstart=`), and prints True unless the first reads reused and the second does not: True while open, and True for a fix that compares in local time. A Windows host prints True (the closure is read on POSIX). | minor | LOGIC_BUG | MAINTAINER |

| `DEF-3014` | espalier/sandbox_posture.py::read_state and ::doctor_lines (the sandbox read as on from the settings alone; no dependency check on Linux and WSL2) | **`espalier doctor` reports the sandbox on where it may never start: on Linux and WSL2 it reads the posture from the settings alone, and nothing checks the sandbox's dependencies there.** `espalier/sandbox_posture.py::read_state` sets `supported` to "not native Windows", and `::doctor_lines` prints `sandbox: on (sandbox.enabled true in ...); all N posture entries present` from the settings files. Nothing in `espalier/`, `tools/cc/` or `docs/` names bubblewrap or socat, and the posture never names `sandbox.failIfUnavailable`. Claude Code's sandboxing page (code.claude.com/docs/en/sandboxing, read 2026-10-18) says Linux and WSL2 need `bubblewrap` and `socat`, and that "if the sandbox can't start because a dependency is missing or the platform is unsupported, Claude Code runs commands without sandboxing" unless `sandbox.failIfUnavailable` is true. Found in DEF-5005's Task 0 (2026-10-18): this Windows box's WSL2 distro, Ubuntu 24.04.5, has neither package installed, so a session there with the posture on would read `on` in doctor while its shell reads run unsandboxed. Not driven: Claude Code is not installed inside that distro, and whether Claude Code prints its own warning at startup is not measured; neither changes what doctor claims. The same class: a WSL1 distro (the page: "Sandboxing requires WSL2") reads as supported too. Who is hurt: an adopter on Linux or WSL2 who runs `init --sandbox-posture`, turns the sandbox on, and reads doctor's `on` as the secret paths being behind it, on a host where a stock Ubuntu image carries neither package. Fix shape: on a POSIX host other than macOS, doctor checks the two binaries on PATH (and WSL1) and, where one is missing, warns that the sandbox will not start and commands run unsandboxed, naming the install line and `failIfUnavailable`; writing `failIfUnavailable` stays the operator's call. Refuted if a session on such a host runs its shell commands sandboxed after all (the page says it does not). The probe plants a tree whose project settings turn the sandbox on, reads it with `::read_state` as a non-Windows host whose `environ` carries an empty PATH, and prints how many warnings `::doctor_lines` returns: 0 while open; a fix that warns where bubblewrap or socat is missing prints 1 or more. A fix that reads PATH from somewhere other than `environ` re-pins it. | minor | LOGIC_BUG | ADOPTER |

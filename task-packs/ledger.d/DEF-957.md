TP-465, 1-B.** PRIOR TEXT: `espalier/cleanup.py::_file_is_managed` decides ownership by the `espalier:managed` marker and so preserves an adopter's own `CLAUDE.md`, skills and commands; `espalier/doctor.py` decides it by path: `espalier/managed_paths.py::fallback_managed_paths` adds every existing member of `STANDARD_MANAGED_ROOT_DOCS` (which lists `CLAUDE.md`, that `init` writes only when none exists, and `.claudeignore`, that nothing writes or reads) plus every file `surface_contract.CLAUDE_KIND_GLOBS` matches under `.claude/agents`, `.claude/commands` and `.claude/skills`, never consulting `managed_markers`; `::managed_paths_from_plan` adds the root docs unconditionally. Two harms. `ownership.managed_paths` names the adopter's `CLAUDE.md` and skill as harness-managed (the plan view names `.claudeignore`; `managed_settings` holds every `.claude/` path, not settings). And `espalier/doctor.py::_deployed_surface_remains`, the DEF-770 uninstall detector, unions the same inventory, so after a complete `clean-generated --execute` an unmarked adopter skill or command under a harness-owned root reads as leftover deploy surface, the uninstalled branch is skipped, and `doctor` exits 1 with `fail: missing required managed surface` and a next step telling the adopter to re-run `init`. Who is hurt: the adopter following the documented uninstall on any tree carrying one file of their own under `.claude/`, told their clean uninstall is a broken install. Driven at 550314e on a minimal tree and on a clone with a tracked skill, each re-driven independently: `doctor` claimed `CLAUDE.md` and the skill; after `clean-generated --execute` it exited 1; with the skill moved out it exited 0 and reported the tree uninstalled; an unmarked adopter command reusing a packaged name (`preflight.md`) gave the same fail. `tests/test_doctor.py::TestDoctorUninstalledTree::test_one_leftover_skill_file_keeps_the_broken_install_verdict` pins the misread: its leftover fixture carries no marker, which is the adopter's shape, not a deploy's. Fix shape, one predicate: count a `.claude/` path in `_deployed_surface_remains` only when `managed_markers.file_carries_marker` holds (a real leftover is marked, because the uninstall deletes marked files); split `ownership_summary` by the same predicate into marker-bearing files and a bucket for files `init` wrote that the adopter now owns, persisting `_CLAUDE_MD_SKIPPED_MARKER`'s answer so `CLAUDE.md` is listed only when generated; drop `.claudeignore` from the adopter plan view; add a doctor-equals-clean-generated parity test on one tree, the property that would have caught DEF-556 and this.

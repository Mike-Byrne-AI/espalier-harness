| `DEF-1093` | espalier/cli.py::_deploy_asset_md; espalier/cli.py::_packaged_md_assets; espalier/models.py::HarnessConfig; espalier/render_surface.py; espalier/assets/docs/TROUBLESHOOTING.md (skillOverrides) | **There is no durable, declared way to retire a shipped Espalier asset: the deploy loop reads no config, so a deleted asset is re-created, and the one documented off-switch is per-machine and invisible to the engine.** `espalier/cli.py::_packaged_md_assets` enumerates every packaged `.claude` body and the `deploy_harness` loop calls `_deploy_asset_md` on each without reading `espalier.toml`; `_deploy_asset_md` returns `created` for any absent path, so `init` and `upgrade --execute` bring back a command or agent the adopter deleted to keep a native one of the same job. The checks then treat the deletion as damage: PACK_MANIFEST is built from the packaged surface whether or not the file is on disk, so audit and doctor report a missing promised file, and `upgrade` never reaches its nothing-to-do line. `espalier/models.py::HarnessConfig` has no per-asset key (`surface_mode` gates only generated docs), and the only documented route, `skillOverrides` in `espalier/assets/docs/TROUBLESHOOTING.md`, lives in per-machine `settings.local.json`, is documented for two name collisions only, and is read by no engine code, so COMMANDS.md, the core flow and the banner keep presenting the asset. An unmarked stub at the Espalier path does work (`skipped_user_file`), but it stays a live slash command, stays in the command table, is re-announced as `kept as yours` on every upgrade, and is documented nowhere. Found by the 2026-10-03 adoption audit (`espalier-issues/audits/2026-10-03-adoption/public_report.md`, B-2); re-checked at `08ab2db`: LIVE (the doctor-fails-on-one-deleted-command behaviour is pinned by an existing test). Two precedents exist to copy: the `goal_snapshot` opt-out and the statusLine rule that a present key is the operator's. The hook half is partly by design: the deploy ignores on-disk state when choosing hook scripts (the iteration invariant) so an agent cannot shrink the deploy set to silence a gate, so a config list must not cover the four blocking gates. Who is hurt: an adopter whose repo already has its own `/ship` or `/review` and who wants Espalier's out, and gets it re-created at the next upgrade. Fix shape: add a `retire_assets` list to `espalier.toml` with a required reason per entry, read by the deploy loop and `preview_managed_surface`, PACK_MANIFEST, the surface gate, doctor (an info line) and the rendered command table and core flow; keep retirement of write_guard, plan_guard, config_guard and stop_gate a loud doctor state. | minor | LOGIC_BUG | ADOPTER |

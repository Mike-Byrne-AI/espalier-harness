| ~~`DEF-5060`~~ | espalier/_rmtree.py::_add_owner_bits (os.stat and os.chmod follow a link out of the tree) | ✅ **CLOSED 2026-11-02 — `espalier/_rmtree.py::_add_owner_bits` reads the mode by `lstat` and sets it on the path itself, never through a link: with `follow_symlinks=False` where `os.chmod` takes it (macOS; Windows from 3.13), bare on Windows to 3.12, and not at all on a link elsewhere (Linux, where a link's own mode never refuses an unlink). The defect was POSIX alone: a bare `os.chmod` on Windows never follows a link (to 3.12 its one body sets the path's own attribute; from 3.13 `follow_symlinks` defaults to false there, `CHMOD_DEFAULT_FOLLOW_SYMLINKS` in CPython's `Modules/posixmodule.c`, read for both, a correction the lane's code review made to the fix shape above). The stdlib twin `scripts/wheel_smoke.py::_remove_tree_clearing_bits` had the same shape and now calls its own `_add_write_bit` with the same three arms. Pinned by `tests/test_rmtree.py::TestALinkIsDeletedNeverFollowed` (the row's drive through `remove_tree`, strict and best effort, and through `remove_file`, each red at the base by its assertion; the three chmod arms through a fake on any host; a Windows-only behaviour pin asserting a read-only link refuses a bare unlink, for portability's windows-latest leg, not driven on this host) and `tests/test_wheel_smoke.py` (`test_neither_twin_lends_a_refused_links_target_the_write_bit`, both deleters on one shape, red at the base for both; `test_both_twins_take_the_same_chmod_arm`, all three arms in both). The probe reads `outside_mode=0o400` at the head and `0o600` at the base.** PRIOR TEXT: **`espalier/_rmtree.py`'s bit helper (`_add_owner_bits`, which `_add_write_bit` calls) reads and sets the mode through `os.stat` and `os.chmod`, both of which follow a symlink, so a refused unlink of a link inside the tree gives the link's TARGET the owner write bit, even when the target lies outside the tree: the module's own rule, clear bits only on what you were asked to delete, does not hold for a link.** A 0o500 directory inside the tree holding a link to a 0o400 file outside it: the unlink of the link refuses (the directory's write bit governs it on POSIX), the handler adds `S_IWUSR` to the path that refused, which resolves to the outside file, and that file is 0o600 after `remove_tree(..., best_effort=True)` returns, the same at HEAD 54caffb and on the DEF-5054 lane (found by that lane's code review, 2026-11-02). Who is hurt: an adopter whose `espalier cleanup` or `fuse` rollback meets a link inside a write-protected directory of the tree, and who is left with a file outside the tree made writable. Fix shape: the helper reads the path with `lstat` and leaves a link's target alone, setting the link's own bits only where `os.chmod` takes `follow_symlinks=False` (macOS; Windows from 3.13, where the read-only attribute of the link itself is what refuses an unlink); on Linux a link's own mode never refuses, so skipping it loses nothing. Its own oracle is a Windows read of a read-only link on each interpreter, which this host cannot make. | minor | LOGIC_BUG | ADOPTER |

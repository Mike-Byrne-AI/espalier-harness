| `DEF-5060` | espalier/_rmtree.py::_add_owner_bits (os.stat and os.chmod follow a link out of the tree) | **`espalier/_rmtree.py`'s bit helper (`_add_owner_bits`, which `_add_write_bit` calls) reads and sets the mode through `os.stat` and `os.chmod`, both of which follow a symlink, so a refused unlink of a link inside the tree gives the link's TARGET the owner write bit, even when the target lies outside the tree: the module's own rule, clear bits only on what you were asked to delete, does not hold for a link.** A 0o500 directory inside the tree holding a link to a 0o400 file outside it: the unlink of the link refuses (the directory's write bit governs it on POSIX), the handler adds `S_IWUSR` to the path that refused, which resolves to the outside file, and that file is 0o600 after `remove_tree(..., best_effort=True)` returns, the same at HEAD 54caffb and on the DEF-5054 lane (found by that lane's code review, 2026-11-02). Who is hurt: an adopter whose `espalier cleanup` or `fuse` rollback meets a link inside a write-protected directory of the tree, and who is left with a file outside the tree made writable. Fix shape: the helper reads the path with `lstat` and leaves a link's target alone, setting the link's own bits only where `os.chmod` takes `follow_symlinks=False` (macOS; Windows from 3.13, where the read-only attribute of the link itself is what refuses an unlink); on Linux a link's own mode never refuses, so skipping it loses nothing. Its own oracle is a Windows read of a read-only link on each interpreter, which this host cannot make. | minor | LOGIC_BUG | ADOPTER |

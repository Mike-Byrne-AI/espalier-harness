| `DEF-5017` | tools/cc/hooks/_zone_watch.py::content_digest (a file of BIG_FILE_BYTES or more is identified by stat:<size>:<mtime>); tools/cc/hooks/_zone_watch.py::_blob_holds (which never matches it against git's blob) | **A protected file of 4 MiB or more never reads as git's, so a pull or a checkout that brings it back to its committed content still reports it.** `tools/cc/hooks/_zone_watch.py::content_digest` identifies a file of `BIG_FILE_BYTES` or more by `stat:<size>:<mtime>` and never reads it, and `::_blob_holds` compares that against the blob git returns, which never matches, so path 2 cannot account for a big file, in the outer repository or (since DEF-4012) in a nested checkout. Found by DEF-4012's code review (driven: a 5 MB `weights.bin` pulled inside `models/clone` reports). Who is hurt: an adopter protecting a directory of model weights or datasets (DEF-4012's own `models/` user), told to stop on every pull or checkout that touches a large file -- the guard's one right response to a report is to stop, so a false one costs a halt and teaches the agent to read the report as noise. Named, not seen in an adopter. Fix shape, untested: for a big file, ask its checkout's git whether it is clean against `HEAD` (`git diff-index --quiet HEAD -- <path>`, which reads the index's stat first), or hash it with `git hash-object` in a bounded spawn, inside the after-check's time budget.

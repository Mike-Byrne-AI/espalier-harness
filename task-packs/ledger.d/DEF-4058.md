| `DEF-4058` | tools/cc/hooks/stop_gate.py::_gate_handoff (no read of the seat's open pull requests; its denial text names the handoff alone) | **`stop_gate`'s handoff gate tells a seat whose first pull request is still in CI to hand off its second lane, which the one-open-pull-request rule says to hold, and the ship driver would open the second pull request beside the first.** `tools/cc/hooks/stop_gate.py::_gate_handoff` blocks the Stop once per commit when nothing is in flight and the branch holds commits its upstream does not, with `GATE_HANDOFF_OWED` ("Run /handoff: ... pushes the lane once, opening the pull request with auto-merge armed"). Its ways through are a plan in progress, a tracked edit, an own-clear marker armed at HEAD (DEF-4057) and a repository whose handoff does not push; none reads the seat's open pull requests, which `tools/cc/ship.py::seat_open_prs` reads at `open` only to note "this one opens beside it" (the driver does not refuse). The protocol's item 4 (memory/parallel-work-protocol.md, "One open pull request per seat") has the seat start its next job at once on a new branch and open its pull request when the first merges, so the gate and the rule disagree on the day's commonest shape: a worker commits its second lane while its first is in CI (air-work shipped #376 at 12:34Z on 2026-10-31 and claimed its next lane at 12:46Z, the merge coming at 13:2xZ). Measured so far: the two Gate 5 blocks on the Mac audit logs of 10-30 and 10-31 are both the dispatcher's one-lane days (08:58Z and 08:30Z, 1 commit ahead each), and no worker's block with a pull request open is on them (the Windows seats' logs are on their box), so the harm is read from the code, not yet counted. Who is hurt: the worker seat holding a finished second lane and an open first, told by a blocking gate to do what the brief says not to (a gate obeyed opens a second pull request whose CI never tested the first's merge; a gate disobeyed is a gate learned to disobey); the dispatcher reading two open pull requests on one seat.

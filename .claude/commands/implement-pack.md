Execute one or more task packs (`TP-*.md`) end-to-end with the established
single-atomic-commit-per-pack workflow. Auto-continues to the next pack
unless a defined stop condition fires.

## Usage

```
/implement-pack <path-to-TP-NN.md>          — single pack
/implement-pack <path-to-folder/>           — every TP-*.md in the folder, in order
/implement-pack --resume                    — continue from cc/execution_plan.json
```

The folder mode processes files matching `TP-*.md`, sorted numerically by
the leading TP-NN. Files like `README.md`, `MASTER_EXECUTION_PLAN.md`, and
`MERGE_NOTES.md` are skipped — those names are illustrative, whichever
such files your repo keeps. The user's exact filename is used when given
a single pack — never substituted.

## Per-pack workflow

Pack-artifact review (step 0-A) runs before the
scope-check (step 0-B). Step 0-A catches mechanical errors
— wrong line numbers, missing symbols, false prose claims, stdlib-rule
violations in code examples — that confound 0-B's structural
reachability analysis. Both gates run before any sub-task executes.

0-A. **Pack-artifact review.** Before reading the pack as
   input for execution, run the mechanical fence check, then dispatch the
   `code-reviewer` agent with its output in hand — a machine result before
   the agent forms an opinion, not after.

   ```
   # Espalier source repo only -- not deployed by init; elsewhere, read the pack's fences by eye
   python scripts/check_pack_fences.py <pack-path>
   ```

   (Espalier-Harness self-host step — an adopter repo has no `scripts/`, so
   skip it and rely on checklist items 1 and 2 instead.) It resolves every
   fence tagged ``python target=<path>`` against the module the pack says it
   edits and reports any name bound nowhere in that module — a `NameError` in
   prescribed code, found before anyone pastes it. **Read its coverage line as
   part of the result:** `0 checked` means nothing was verified, which is not
   the same as clean.

   Then dispatch the `code-reviewer` subagent (`subagent_type='code-reviewer'`) with:
   - Pack file content (read the path you were given).
   - The fixed checklist below (the Pack-artifact review checklist, v2),
     pasted in full into the agent prompt:
     <!-- pack-artifact-checklist: BEGIN generated region -- do not hand-edit. Regenerated by scripts/sync_checklist_regions.py, Espalier-Harness self-host tooling; an adopter repo has no scripts/ and never runs it. -->
     1. Line-number accuracy. Every `file.py:N` reference resolves to a
        line that exists in the named file. Surrounding context matches
        what the pack claims.
     2. Symbol-name accuracy. Every function / class / constant cited
        exists at the named path. Spot-check a representative sample of
        cited symbols.
     3. Cross-pack dependency. If the pack modifies files also modified
        by another in-flight pack, the dependency is spelled out in a
        "Cross-pack coordination" section.
     4. Test-naming consistency. Test classes follow the `TestX` pattern;
        test functions follow `test_{specific_behavior}` per the project's
        CONVENTIONS.md.
     5. Bypass-class numbering. If the pack adds `BC-NNN` corpus rows,
        the numbers are contiguous with the current corpus state, OR
        explicit non-contiguous numbering is documented.
     6. Conflicting prescriptions. The pack does not prescribe a change
        that another in-flight pack reverses.
     7. Effort calibration. Per-sub-task estimates are not wildly off
        for the scope listed. Total matches sum of parts.
     8. Pass-criteria realism. Each pass criterion is either testable
        OR documented as a manual smoke. None are mutually inconsistent.
     9. Surface additions and removals declared. For every path in the
        pack's `### Added-paths` and `### Removed-paths`, the pack's
        `## Implementation` also updates the applicable count constants,
        name-sets, `.claude`/vendor/asset mirrors,
        `PACK_MANIFEST`/`LIVE_SURFACE`/`COMMANDS` regens, and the integrity
        manifest — in reverse for a removal, plus a sweep of inbound
        references — cross-check against `espalier surface-impact` (0-D)
        output. A file can pass items 1–8 and 0-B cleanly yet trip a
        count-pin, mirror-parity, hygiene, or provenance contract only the
        full suite catches.
     <!-- pack-artifact-checklist: END generated region -->
   - Output format spec: "for each checklist item, report severity
     (BLOCK / WARN / NIT / PASS) with file/line
     evidence per finding, formatted as
     SEVERITY • PACK_LINE • CLAIM • REALITY • SUGGESTED_FIX."

   When the agent returns:
   - If any BLOCK — surface findings to the operator. Operator edits
     the pack file, then re-invoke `/implement-pack` from the
     beginning.
   - If WARN only — surface as advisory. Operator acknowledges, then
     proceed to 0-B.
   - If only PASS — proceed to 0-B.

   The checklist is versioned. Record the version label
   (e.g., `Pack-artifact review checklist v2`) in the blueprint
   reasoning entry so historical reviews are reproducible.

   This step is non-skippable. Packs authored before this review step
   existed are reviewed the same way at first execution; no
   bulk-retroactive mode is needed.

   No standalone orchestrator script exists — agent dispatch is a
   Claude-Code-internal capability invoked directly from this
   slash-command body by naming the subagent (`subagent_type='<name>'`).

0-B. **Pre-flight scope-check.** Before reading the pack as input,
   run `python -m espalier scope-check <pack-path>` to surface the reference graph
   for every symbol the pack proposes to change. Exit code semantics:
   - 0 = no scope gap, or you've accepted the gap with
     `--accept-scope-gap "<reason>"`.
   - 1 = nothing parsed — no symbol and no literal came out of the pack,
     whether because neither `## Affected symbols` nor `## Affected
     literals` is declared or because a declared section parsed to zero
     entries (the output names the cause: an unrouted sub-heading, bullets
     with no backticked token, none-declarations, an empty literals
     section). When the output carries a `scope-check: DECLARED_BUT_EMPTY
     --` line, stop and fix the pack (see `docs/PACK_AUTHORING.md`): a
     declared blast radius was never walked. When it says the bullets
     declare nothing on purpose, or no section is declared, that is a
     clean skip — proceed. A literals-only pack (a pure rename with no
     symbol changes) is a supported shape and DOES run.
   - 2 = scope gap present. Read the report; either widen `Scope (in)`
     to cover the gap or proceed with `--accept-scope-gap` and a
     written reason. The test suite is still the actual gate; this is
     a pre-flight signal, not a hard block.

   Skip this step only if the pack declares NEITHER an `## Affected
   symbols` NOR an `## Affected literals` section. Note in the per-pack
   execution plan that scope-check was not run.

0-C. **Compression probe.** After 0-B clears, run
   `python tools/cc/sister_site_probe.py --json`. Read the `scope`
   block before the verdict: it names whose code was scanned. On an
   adopter tree the gating scope is YOUR Python source (the whole tree
   minus junk, `tests/`, dot-directories, nested repos and the harness's
   own zones — on a fused tree, the whole overlay; narrow it with
   `--roots src/`), and the exit code keys on that scope
   alone. Espalier's deployed hooks under `tools/cc/hooks/` are scanned
   too but reported under `harness_internal` (text: HARNESS-INTERNAL):
   advisory, never gating, and not yours to fix — `write_guard` keeps
   those files read-only, so report that debt upstream. `scanned_count:
   0` means the probe never looked at your code (pass `--roots`), not
   that it is clean. On the harness's own source tree the scope is
   `tools/cc/hooks/` + top-level `espalier/`, every arm gates, and the
   report has no advisory tail. Exit code semantics:
   - 0 = nothing blocking-class in the gating scope: no 3+ identical
     function cliques and no 3+ identical constant cliques (on the
     harness source tree, also no canon-misses and no alias-misses).
     A 3+ identical clique that is DELEGATING (every site forwards to
     one imported owner via pass-through args) is advisory, not debt —
     the report labels it and names the owner.
   - 1 = a `--roots` path does not exist or lies outside the repo.
   - 2 = compression debt present in the gating scope. Read the report;
     either fix the duplicate before invoking `/implement-pack` again,
     or proceed with `--accept-compression-debt "<reason>"` and a
     written reason. The probe is a pre-flight signal, not a hard
     block; the convention is "compress upstream, not pin downstream."

   DIVERGENT cliques (same name, different bodies — e.g. every hook's
   `main`) are advisory; they do not block. The override is recorded
   in the per-pack blueprint reasoning entry.

0-D. **Surface-impact pre-flight.** After 0-C clears, run
   `python -m espalier surface-impact <pack-path>`. It reads the pack's
   declared `### Added-paths` and `### Removed-paths` (a path-shaped
   `### Renamed` entry is read as the removal of its old name; a new CLI
   subcommand registered inside an existing file is detected too), matches
   each to its shipped surface, and prints the count pins / mirrors /
   hygiene / provenance obligations the full suite will demand once those
   files land or leave -- a removal names the same sites in reverse
   (decrement the count, drop the row, let the mirror sync prune, refresh
   the manifest). Exit code semantics:
   - 0 = no public surface additions or removals (or acknowledged with a
     reason).
   - 1 = pack file missing / not a file.
   - 2 = public surface addition(s) or removal(s) present. A `(renamed)`
     line whose trigger is a file the pack does not delete means the
     pack's `### Renamed` bullet leads with a path: fix the bullet
     (`path::symbol`), do not accept the gap. Read the obligation map and
     BUNDLE the implied SoT edits (count constants, name-sets, mirrors,
     `PACK_MANIFEST`/`LIVE_SURFACE`/`COMMANDS` regens, integrity refresh)
     into the execution plan up front — or proceed with
     `--accept-surface-gap "<reason>"` and a written reason.

   Advisory, like 0-B/0-C: a signal, not a hard block. It closes the gap
   where a pack passes 0-A/0-B/0-C clean yet trips a count-pin,
   mirror-parity, hygiene, or provenance contract only in the full suite
   (the file a pack ADDS is auto-enrolled in those contracts —
   `classify_release_path` routes every un-ruled path to `public`).

1. **Read the pack spec.** Load it as input — even if you remember it,
   re-read. `## Task 0 — Verify` and `## Pass criteria` are the contract.
   Record `git rev-parse HEAD` now as the pack baseline — step 6's review
   needs it to diff the pack's own work, and in folder-mode auto-continue
   `HEAD~1` is the *previous* pack's commit, not this one's starting point.

1b. **Recall the hazards of the pack's `Affected` files, not the pack's
   title:** `/recall <the artifact's idiom or the failure shape>` for each
   surface the pack names (the same rule as `/implement-task` step 1, with the
   same 2026-09-06 measurement behind it: task text recalled none of four
   applicable entries, hazard words recalled all four).

2. **Two separate checks — do not merge them.** They fail for different
   reasons and have different exits, and reading one as the other is how a
   pack's own kill switch gets read, passed, and never pulled.

   **2a — Audit current state (is the premise still true?).** Run the pack's
   own greps and targeted-test commands against the live repo. Confirm the
   pre-state the spec describes still matches what you see — if it doesn't,
   that's a stop condition (the pack assumed a state that no longer holds).

   **2b — Execute `## Task 0` (is the FIX still the right one?).** A premise
   can be perfectly current while the prescribed fix is wrong or inert. Run
   the oracle the pack names, compare its output to the pack's stated
   **refuting result**, and take the exit the pack declares.
   - If the oracle refutes the prescription: **stop and re-raise.** Do not
     adjust the fix and continue. The approval was granted against a stated
     reason; when measurement kills the reason, the approval is gone with it.
     Stamp `State: SCRAPPED` per step 12 with the measurement as the reason —
     that path does not require a commit — and report.
   - If the pack has no `## Task 0`, say so explicitly in the report rather
     than treating its absence as a pass. Older packs predate the section;
     an absent gate is an unknown, not a green one.

3. **Draft `cc/execution_plan.json`** with one step per pack phase:
   ```bash
   python tools/cc/execution_plan.py create \
     --task "<pack ID>: <one-line>" \
     --goal "<pack motivation in one short sentence>" \
     --not-doing "<scope-out summary in one short sentence>" \
     --steps "phase1|phase2|phase3|..."
   ```
   Each phase = one logical unit (one cluster of edits, one verification).

   The `--goal` and `--not-doing` flags populate plan-level metadata
   that every subsequent `mark <i> running` replays as an
   `action_justification` entry on the active blueprint
   (auto-compose). Both flags are required together to enable
   auto-compose; passing only one falls through to the existing
   advisory.

4. **Create TaskCreate items** mirroring the phases so progress is visible
   in the harness UI. Mark each completed as soon as it's done; don't batch.

5. **Execute phase-by-phase.** For each phase:
   - Mark execution_plan step `running`.
   - Make the changes.
   - Run targeted proof (the specific test for the phase, not full suite).
   - If the phase added or removed a shipped surface, run its registration
     contract now — these fire only in the full suite otherwise. Use the
     **0-D surface-impact** obligation map as the checklist; the surface set is
     broader than the old "(CLI subcommand, test file, agent/command/skill)"
     shorthand: slash command / agent / skill (count pins + 3-way mirror +
     tables), hook entry or helper (hook counts + vendor mirror + integrity),
     dev script (`EXPECTED_SCRIPT_NAMES`; the count is derived from it),
     seed/portable doc (`_SEED_DOC_REL_PATHS` + asset byte-mirror +
     `_DOCS_ASSET_TAILS`), shipped `docs/` (hygiene + broken-links), packaged
     asset (byte-mirror), and a new CLI subcommand (cheat-sheet CLI parity).
   - If the phase touched `tools/cc/` or `espalier/`, run `python -m espalier
     provenance .` now — unconditional on THIS repo (it stands down and exits 0
     elsewhere), not gated on "added a new surface": a
     build-history tag (`TP-NNN`, `round-N`, `wf_…`) leaks just as easily from a
     plain comment edit, and a `tools/cc/` comment byte-mirrors into the shipped
     `espalier/_vendor/cc/`. It is ~1s (the fast twin of the full-suite gate), so
     it catches the tag mid-phase instead of at the step-6 full suite or (worse)
     after the commit. Exit 2 → strip the tag (keep the content) / allowlist it.
   - Mark step `passed` and move on, or `failed --note "..."` and stop.

6. **Orthogonal-context review first (conditional), then the one integration run.**
   The review comes FIRST because its findings are edits, and an integration run
   started before they land is stale when they do (measured 2026-09-06: two full
   runs started early were killed the same day for exactly this). The integration checks
   below prove the suite is green; they do not prove the code the pack *wrote* is
   correct. The ambient
   net that would (`stop_gate` Gate 3 — which blocks once per session asking for a
   `code-reviewer` dispatch, and self-clears whether or not one happens) is **off during
   pack execution** — bypassed under `ESPALIER_MAINTENANCE_MODE` (which harness-touching
   packs launch with) and never fired between packs in folder-mode auto-continue. So
   dispatch the orthogonal-context review here, gated on what the pack touched:
   - If any phase changed `tools/cc/`, `.claude/`, `.github/workflows/`, `bench/`,
     `scripts/`, or `espalier/` engine code → dispatch the `code-reviewer` subagent
     (`subagent_type='code-reviewer'`) on this pack's diff (the working diff before
     commit, or `git diff <baseline>..HEAD` after, where `<baseline>` is the
     `git rev-parse HEAD` recorded at step 1). (`bench/` gates releases; `scripts/`
     holds the mirror-sync + release tooling — both governance-load-bearing, not routine.)
   - If the pack ships or modifies a hook, a gate, or a command / agent / skill body
     → ALSO dispatch `failure-mode-reviewer` (the `/adversarial` lens). Command bodies
     count: they are the instruction layer this workflow runs on.
   - Doc-only or test-only packs skip this — the mechanical gates above are sufficient
     and an agent pass would only add latency. "Config-only" is NOT a skip: a
     `.claude/` change is a governance change.

   Dispatch both in one message and **freeze edits until both reports are in**; read
   the failure-mode report second (its frame assumes the code is correct); land the
   accepted findings from both as ONE fix batch and re-run the affected phase proofs.
   A fix applied mid-review makes the second reviewer re-derive against a tree that
   moved under it (measured twice, 2026-09-06).

   Stop conditions, per agent vocabulary — the two agents do not share one:
   - `code-reviewer`: a **BLOCK** finding, OR a **REQUEST CHANGES** /
     **NEEDS DISCUSSION** verdict, stops. WARN / NIT are advisory.
   - `failure-mode-reviewer`: a **REGRESSION** finding or a **REQUEST CHANGES** verdict
     stops. GAP / ROUGH-EDGE are advisory.

   On a stop: fix it as part of that one batch, then run the integration check below
   once. If a second review round still stops, surface to the operator rather than
   iterating again.
   Advisory findings get recorded in the blueprint. This mirrors the 0-A pack-artifact
   review, re-aimed from the pack document onto the code the pack produced.

   **Then the integration check — once, after the fix batch.** `git add -N`
   any new file first (the `git ls-files` gates cannot see an untracked one).
   A pack that touched no file under `tools/cc/` and no `.py` under `espalier/`
   outside its byte-mirrors may run the tree-wide contracts here (`pytest -m
   contract -q`; `python scripts/proof_tier.py` computes the answer on the
   Espalier-Harness tree, and prints `recall` with a second line -- the recall
   engine's own test files -- when the pack touched a file the pull-recall
   corpus reads) and leave the full suite to the handoff's preflight;
   a pack on the shipped runtime runs it now:
   ```bash
   pytest -m contract -q                                  # no runtime change: the tree-wide contracts
   pytest -q                                              # runtime changed: the full suite (adopter tree)
   python scripts/proof_tier.py --run                     # Espalier-Harness tree: the tier the pack earns (full is both halves, recall the contract slice then the recall tests, plus a changed script's own test file on the cheaper tiers), one receipt
   python -m espalier pre-release . --skip-tests --skip-parity  # release gate
   python -m espalier audit .                             # zero findings
   ```
   The release gate is Espalier-Harness's own: it validates *Espalier's* release
   artifact against *Espalier's* PyPI requirements. On any other repo it stands
   down and prints `{"status": "skipped"}` at exit 0 — so on an adopter tree
   `pytest -q` and `espalier audit .` are the two integration gates that actually
   run, and a `skipped` here is the expected answer, not a gate that passed.
   If any hook script under `tools/cc/hooks/` or any file under
   `espalier/` changed, refresh the integrity manifest:
   ```bash
   python -m espalier integrity refresh .   # maintenance mode is already set at launch (see below)
   python -m espalier integrity verify .
   ```
   (Do NOT inline a maintenance-mode env assignment on these — write_guard denies
   an inline harness-env assignment in a tool call and the denial also drops a
   bundled command; the mode is inherited from the parent-shell launch.)

7. **Update `CHANGELOG.md`** under `[Unreleased]` *(skip if this repo
   keeps no changelog — the file is not deployed by `init`)*. Use the existing
   subsection convention (Breaking changes / Fixed / Changed / Added —
   one entry each at most; merge into the existing subsection rather
   than creating duplicate `### Changed` blocks. The
   `TestChangelogStructure.test_no_duplicate_categories_per_release`
   contract enforces this.).

8. **Sync any SoT mirror** *(Espalier-Harness self-host step — an adopter repo has no `scripts/`
   mirror tooling and ships no mirrored assets, so skip this step).* If the phase touched
   `.claude/{agents,commands,skills}/<file>.md` — the SINGLE SOURCE OF TRUTH
   (hand-edit HERE only) — regenerate BOTH generated mirrors by running
   `python scripts/sync_claude_mirrors.py` (Espalier source repo only). It copies each SoT file into
   `espalier/assets/claude/{agents,commands,skills}/` (wheel package-data) AND
   `examples/dogfooding/.claude/{agents,commands,skills}/` (the adopter-facing
   reference) — a **three-leg** mirror; a hand-edit that updates only one leg
   fails parity. The byte-parity is pinned by
   `tests/test_package_resource_parity.py` (Espalier source repo; `TestRootMirrorParity` root↔dogfooding
   + `TestAssetClaudeMirrorParity` asset↔dogfooding). Never hand-edit a mirror.

9. **Record a blueprint reasoning entry** so cross-pack context survives
   compaction and resumes:
   ```bash
   python tools/cc/cognitive_blueprint.py record --kind decision \
     --description "<TP-NN> shipped: <one-line>; commit <sha>"
   ```

10. **Commit.** Single atomic commit per pack. Stage only the files the
    pack touched plus the integrity manifest. Use the established commit
    message shape: type-scope subject line referencing the pack ID,
    multi-paragraph body explaining what changed and why, verification
    block at the end, `Co-Authored-By: Claude, Scion <claude@espalier.dev>`
    (adopter-neutral default — set your project's own co-author trailer if you
    keep one).
    Commit with a plain `git commit` (use `git commit -F <file>` for a
    multi-paragraph body). Maintenance mode is already active from the
    parent-shell launch below, so do NOT prefix the commit with an inline
    maintenance-mode env assignment: write_guard denies an inline harness-env
    assignment in a tool call (it cannot reach an already-running hook), and the
    denial also skips a bundled `git add` — risking a partial commit.

11. **Close the execution plan.** After the commit lands, run
    `python tools/cc/execution_plan.py status` and confirm it reads
    `complete` (every step `passed`). If a step is still `running` or
    `pending` — the pack landed but the tracker was never closed — mark it
    with `python tools/cc/execution_plan.py mark <i> passed`. A pack that
    lands with an open plan makes the *next* session's compact-orientation
    banner surface this finished pack as the in-flight `ACTIVE PLAN (live --
    this is where you were)`, pointing the next session at completed work.
    The plan file is gitignored local state, so this is housekeeping — no
    commit.

12. **Stamp the Landing stanza and move the pack to `Done/`.** After the
    commit lands and the plan reads `complete`, the pack is finished — record
    it and file it away so it stops showing as in-flight work:
    - Update the pack's `## Landing` stanza in place: set `State: LANDED`
      (**bare value — write `State: LANDED`, not `State: **LANDED**`**; the
      `check_pack_landing.py` regex tolerates a bold *label* `**State:**` but
      not a bold *value*, so a bolded value reads as "no State: line"), and
      fill `Commits:` (the SHA from step 10), `Suite:` (the step-6 numbers),
      `Earn-the-red:` (what reds you took), `Red-team:` (step 6's lanes and
      their verdicts — *"ran, none found"* is a result worth recording, not an
      empty field), `Reach:` (members closed / deferred, if the pack claimed a
      class), and `Date:`.
    - Move the file. On an adopter tree `task-packs/` is gitignored local state
      (init's default): `mkdir -p task-packs/Done && mv task-packs/<TP-NN>-*.md
      task-packs/Done/` is housekeeping — **no commit**. On a tree that tracks its
      active packs (the harness's own repo does since 2026-09-21, `Done/` staying
      gitignored) two things differ. First, re-key every ledger row that cites
      `<TP-NN>` BEFORE the move: after it the id resolves in neither shipped
      location and `test_live_ledger_grows_no_new_dangling_id_references` reds;
      `command grep -n '<TP-NN>' task-packs/FORWARD_LEDGER.md` is the census, and
      the re-key goes through `scripts/ledger_row.py` *(self-host only — not
      deployed by `init`; an adopter's ledger, if they keep one, is theirs to
      edit)*, never a hand edit. Second,
      the move is a tracked deletion, in this order and with the pathspec quoted
      (an unquoted glob that no longer matches aborts the whole line under zsh, and
      `git mv` would force-track the pack inside the ignored folder):
      `git rm --cached -- "task-packs/<TP-NN>-*.md" && mkdir -p task-packs/Done &&
      mv task-packs/<TP-NN>-*.md task-packs/Done/`; land the deletion with the
      pack's commit.
    - Confirm with `python scripts/check_pack_landing.py` *(self-host only — not deployed by `init`;
      adopters read the `## Landing` stanza directly)*: it must report
      *"all packs in Done/, Scrapped/ carry a terminal State:"* under a `SCOPE`
      line whose `Done/` count is non-zero (a `SCANNED NOTHING` line in its place
      means the folder was not read, not that it is clean). A pack left in `task-packs/` after
      landing re-surfaces as pending work next session; a pack moved to
      `Done/` without a terminal `State:` trips this check.
    - A pack that was deliberately abandoned stamps `State: SCRAPPED` (with a
      one-line reason) instead and moves the same way. ⚠ **This path does not
      require a commit and is reachable from step 2b.** The rest of step 12 is
      written for the after-the-commit-lands case; a pack killed by its own
      Task 0 never commits, and stamping it SCRAPPED is exactly how the kill is
      recorded rather than lost. Do not read the step-12 preamble as gating it.

13. **Move to the next pack** (folder mode) — go to step 1 with the next
    file. Or: report final summary (single-pack mode).

## Stop conditions — when to ask before continuing

Auto-continue is the default. Stop and use `AskUserQuestion` ONLY when
one of these fires:

- **Test failure** — any pytest failure that isn't already documented in
  `ESPALIER_MEMORY.md` as a known pre-existing unrelated failure. Don't auto-fix
  test failures across packs; the user needs to triage.
- **The release gate fails.** `espalier pre-release` is the contract — on the
  Espalier-Harness source tree. Everywhere else it stands down at exit 0, so
  this stop condition never fires and it is not the interlock protecting your
  chain; the pytest and `espalier audit .` conditions above are.
- **`espalier audit .` reports errors or warnings.**
- **`integrity verify` reports drift** that wasn't expected from the
  files this pack touched.
- **An acceptance-criteria line cannot be verified** by the pack's own
  verification command. Quote the failing line and what you found.
- **`## Task 0`'s oracle returned the pack's stated refuting result** — the
  premise holds but the prescribed fix does not. This is NOT the
  stale-premise condition above and does not share its exits: the citations
  all resolve and nothing looks wrong, which is exactly why it needs naming.
  **Stop and re-raise with the measurement.** Do not adjust the fix and
  continue.
- **Public-API breaking change detected** — confirm it's documented under
  `### Breaking changes (pre-1.0)` in CHANGELOG before proceeding.
- **The pack contains a `STOP`, `OPERATOR REQUIRED`, `DO NOT
  AUTO-EXECUTE`, or `MANUAL STEP` marker** in its body.
- **A pack-introduced file lands in a path that
  `surface_contract.classify_release_path` cannot classify** (returns
  `public` for something that should be `local_only`, or vice versa) —
  the SoT must agree.
- **CHANGELOG contract test fails** (duplicate `### Changed` headings,
  etc. — fix and re-verify before moving on).

When a stop condition fires, present:
- which pack and phase you stopped at
- the literal output that triggered the stop
- 2-3 specific options (abort the pack / abort the chain / continue with a
  workaround). ⚠ **Order matters and "workaround" is listed last on purpose.**
  Offering it first invites the "adjust and continue" move, which is the one
  response a refuted Task 0 forbids outright — for that stop condition it is
  not an option at all, and the only exits are abort-the-pack (stamp
  `State: SCRAPPED`, re-raise) or abort-the-chain.

## Auto-continue policy

If no stop condition fired after a pack's commit:

- **Single-pack mode:** report the commit SHA + diff stat + verification
  numbers, and stop.
- **Folder mode:** record blueprint entry "<TP-NN> done; advancing to
  <TP-NN+1>" and start step 1 of the next pack immediately. Do NOT ask
  "should I continue?" — that's exactly the friction the user wanted to
  remove.

Final report after the chain (folder mode): one-line per-pack table
(commit SHA / diff stat / verification numbers / time).

## Resume after interruption

If `cc/execution_plan.json` exists with status `in_progress`, `--resume`
re-enters at the first pending step:

```bash
python tools/cc/execution_plan.py status      # see pending step
python tools/cc/execution_plan.py mark <i> running
# ... continue from where the prior session left off
```

In folder mode after a context compaction, the persisted blueprint
chain preserves the per-pack reasoning entries — the harness re-injects
the most recent ones, so confirm which packs are done before advancing.

## What the surrounding harness already does

This command leans on infrastructure that doesn't need re-implementing:

- **`write_guard` + `plan_guard`** enforce protected-zone and plan-required
  rules. If a pack would write to `tools/cc/`, `espalier/`, etc., the
  user must relaunch with `ESPALIER_MAINTENANCE_MODE=1 claude --continue` (PowerShell:
  `$env:ESPALIER_MAINTENANCE_MODE="1"; claude --continue`). Don't try
  to bypass — the parent-shell-launch gotcha (`docs/SHARP_EDGES.md`)
  applies.
- **`stop_gate` gate 4** auto-finalizes the active blueprint at every
  Stop event so per-pack reasoning entries are persisted without manual
  finalize.
- **`post_compact`** re-injects critical context after compaction so a
  long chain survives the conversation getting summarized.
- **`TestRootMirrorParity`** + the count-claim contract tests
  (`tests/test_public_surface_truth_docs.py`, Espalier source repo) catch SoT-mirror drift
  and stale doc claims at pytest time — don't pre-empt them; let them
  fire and react to the failure.

The command's job is the workflow shape; the hooks are the safety net.
